이 차시에서 처음 나오는 말

인코딩
글자를 컴퓨터에 저장하는 방식. 방식이 다르면 한글이 깨집니다. 이 데이터는 요즘 표준(UTF-8)이 아닌 옛 방식(CP949)입니다.
정제 (클렌징)

스펙 (명세)
"무엇을 만들 것인가"를 해석의 여지 없이 적은 문서. 모호함 하나가 곧 AI의 임의 결정 하나입니다.
교차 검증
결과물 하나만 보는 게 아니라 원본과 결과를 나란히 놓고 대조하는 것. "파일이 있네요"는 검증이 아닙니다.

이 차시에서 배우는 것

  • 실무 데이터가 왜 그냥 안 되는지 직접 확인한다
  • 처리 규칙을 스펙 문서로 못 박고, 그 스펙으로 팀을 만든다
  • 결과를 원본과 대조해 검증한다 — 하네스의 마지막 조각
  • (선택) 스펙 쓰는 규칙 자체를 스킬로 만들어 어느 업무에나 쓴다

1. 문제 — 실무 데이터는 깨끗하지 않다

소재는 서울시청 인근 업무추진비 집행 내역입니다. "공무원이 법인카드로 반복 방문한 식당 = 검증된 맛집"이라는 가설로 분석할 수 있는 데이터입니다.

1-2. 이 데이터에 숨은 함정 네 가지

함정내용그냥 두면
인코딩·구분자UTF-8이 아닌 CP949, 쉼표가 아닌 탭한글이 깨지거나 컬럼이 안 나뉨
혼합 필드집행장소 한 칸에 상호와 주소가 같이 — 명동칼국수(서울시 중구 세종대로 21길 48)식당명 집계가 어긋남
명칭 불일치법인명(주식회사 보원에프앤비) vs 간판명, 지점 표기 편차(창고43시청점 / 창고43 무교점)같은 가게가 여러 개로 세어짐
좌표 없음주소만 있고 위경도가 없음지도에 못 올림 (이번 차시 범위 밖)

이 네 가지는 이 데이터에만 있는 특수 사정이 아닙니다. 사내 시스템에서 내려받은 엑셀, 팀마다 다르게 쓴 양식, 오래된 CSV — 실무 데이터는 대개 이렇습니다. 2차시의 "분임조 은어"와 같은 문제가 형태만 바꿔 나타난 것입니다.

2. 개념 — 스펙이 계약이다

4차시에서 팀을 만들 때 도메인·입력·산출물·품질 기준 네 줄을 적었습니다. 데이터 작업에서는 그 정도로 부족합니다. 처리 규칙까지 못 박아야 합니다.

모호한 지시

"식당별로 집계해줘"

  • 같은 가게를 하나로 볼 기준이 없음
  • 법인명과 간판명 중 무엇을 쓸지 AI가 정함
  • 돌릴 때마다 기준이 바뀜

스펙으로 못 박기

"정리식당명 기준으로 집계. 지점 표기가 달라도 같은 상호로 시작하면 별도 집계. 법인명은 사용하지 않음"

  • 판단 기준이 문서에 남음
  • 결과가 재현됨
  • 기준이 바뀌면 문서만 고침

스펙은 사람이 읽는 기획서가 아니라 AI가 실행하는 계약서입니다.
모호함 하나 = AI의 임의 결정 하나. "깔끔하게", "적절히", "보기 좋게" 같은 말이 들어가면 그만큼 결과가 흔들립니다.

3. 실습 A — 스펙 쓰기

AI에게 스펙부터 쓰게 합니다. 바로 작업시키지 않는 것이 핵심입니다.

Claude Code 입력창에 붙여넣기 (map 폴더에서)
식당리스트_실습용.csv 를 분석해 "시청 주변 맛집 랭킹 리포트" 를 만들려고 해.
바로 만들지 말고, 먼저 처리 규칙을 정한 스펙 문서를 MATZIP_SPEC.md 로 써줘.

스펙에 반드시 들어갈 것:
1. 파일 읽는 법 — 인코딩과 구분자를 실제로 확인해서 명시할 것
2. 집행장소 컬럼에서 상호와 주소를 분리하는 규칙
3. 같은 식당으로 볼 기준 (법인명·지점 표기 처리 방침)
4. 집계 항목 정의 — 방문 횟수, 총 집행액, 평균 단가, 최근 방문일
5. 제외 규칙 — 식당이 아닌 항목(매점 등)을 어떻게 다룰지
6. 검증 기준 — 결과가 맞는지 확인할 숫자 (총 건수, 총액 등)

각 규칙은 "적절히", "깔끔하게" 같은 말 없이 실행 가능한 문장으로 써줘.
정하지 못한 것은 [확인 필요] 로 남겨줘.
👀

좋은 스펙인지 보는 법 — 열어서 세 가지만 확인하세요.

  1. 숫자와 값이 적혀 있는가 — "CP949", "탭 구분"처럼 구체적으로. "적절한 인코딩" 이면 실패
  2. 하지 않을 일이 적혀 있는가 — 지도 시각화·리뷰 수집은 이번 범위가 아님
  3. [확인 필요] 가 남아 있는가 — AI가 모르는 것을 정직하게 남겼다는 뜻입니다. 하나도 없으면 오히려 의심하세요

6. 실습 D (선택) — 스펙 쓰는 규칙을 스킬로

선택 실습입니다. 건너뛰어도 다음 차시에 지장이 없습니다. 다만 스펙을 앞으로 계속 쓸 사람이라면 여기가 이 차시에서 가장 남는 부분입니다.

3절에서 스펙을 요구할 때, 프롬프트가 열 줄이 넘었습니다. "반드시 들어갈 것 여섯 가지", "적절히 같은 말 금지", "모르는 건 [확인 필요]" — 이걸 다음 프로젝트에서도 또 씁니다.

2차시의 판단 기준을 그대로 적용합니다. "다음에도 또 나오나?" → 예 → 파일로.
이번에 파일로 만들 것은 업무 지식이 아니라 "좋은 스펙이란 무엇인가"라는 기준입니다.

6-1. 만들기

Claude Code 입력창에 붙여넣기 (map 폴더에서)
방금 MATZIP_SPEC.md 를 쓸 때 내가 요구했던 조건들을 스킬로 만들어줘.
.claude/skills/spec-writer/SKILL.md

description 에 넣을 것 — 언제 쓰는지가 분명하게:
"데이터 처리·분석·자동화 작업을 시작하기 전에 요구사항 명세서를 쓸 때 사용.
 바로 작업에 들어가지 않고 스펙부터 확정해야 하는 모든 작업에 적용."

본문에 넣을 것:
1. 스펙에 반드시 들어갈 항목 — 입력(파일/형식/인코딩) · 처리 규칙 ·
   산출물 형식 · 제외 규칙 · 검증 기준 · 범위 밖(하지 않을 일)
2. 금지 표현 목록 — "적절히" "깔끔하게" "보기 좋게" "알아서" "필요시"
   이런 말이 들어가면 그만큼 AI가 임의로 결정한다는 것을 명시
3. 구체성 규칙 — 값은 실제 값으로 쓴다
   (인코딩은 "CP949", 구분자는 "탭", 기준은 "노출 1,000 미만" 처럼)
4. 모르는 것 처리 — 추측하지 말고 [확인 필요] 로 남긴다
5. 스펙 검수 3문항 — 구체적 값이 있는가 / 안 할 일이 적혔는가 /
   [확인 필요] 가 남아 있는가

파일만 만들고 실행은 아직 하지 마.

예상 결과: 맛집 데이터와 아무 상관 없는 주제인데도 같은 틀로 스펙이 나옵니다 — 입력·처리 규칙·산출물·제외·검증·범위 밖. 데이터가 없으니 [확인 필요] 가 여럿 남습니다. 그게 맞는 동작입니다.

2차시 스킬은 한 업무에서만 쓰였습니다. 이 스킬은 모든 업무에서 쓰입니다.

6-3. 스킬에는 두 종류가 있습니다

업무 지식 스킬일하는 방식 스킬

두 번째 종류를 몇 개 갖고 있느냐가 실력 차이로 나타납니다. 스펙 쓰기 · 회의록 정리 · 보고서 검수 · 데이터 검증 — 이런 "일하는 방식"을 파일로 갖고 있으면 새로운 업무를 만나도 시작이 빠릅니다. 7차시에서 다룰 하네스 100선이 통째로 이 두 번째 종류입니다.

💡

더 정교하게 만들고 싶다면 — 소프트웨어 개발용으로 만들어진 공개 스펙 작성 스킬들이 참고가 됩니다. 데이터 모델·화면 정의·구현 순서까지 항목을 나눠 두는데, "색은 이름이 아니라 hex 코드로", "크기는 ‘크게’가 아니라 픽셀 값으로" 같은 규칙이 핵심입니다. 우리가 "인코딩은 CP949로" 라고 쓴 것과 정확히 같은 원리입니다.

7. 스스로 점검

  • 이 데이터가 "그냥은 안 되는" 이유 네 가지를 말할 수 있다
  • 스펙을 먼저 쓰게 하는 이유를 "모호함 = 임의 결정" 으로 설명할 수 있다
  • MATZIP_SPEC.md 에 인코딩·구분자가 구체적 값으로 적혀 있다
  • 결과를 정답 숫자(15,144건 / 20.3억)와 대조했다
  • "파일이 생성되었습니다" 와 교차 검증의 차이를 안다
  • 스펙 한 줄을 고쳐 결과가 바뀌는 것을 확인했다
  • (선택) 스펙 쓰는 규칙을 스킬로 만들어 다른 주제에 써 봤다
  • (선택) 업무 지식 스킬과 일하는 방식 스킬의 차이를 설명할 수 있다
